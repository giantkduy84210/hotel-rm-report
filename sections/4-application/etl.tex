\subsection{ETL Pipeline}

\paragraph{Extract.}
The source data arrives as two CSV files (one per hotel, H1 and H2) from the public release of Antonio et al.~\cite{antonio2019}. Each row is one booking with 31 variables; the two files share the same schema and are loaded with pandas, then concatenated with a hotel identifier added to distinguish the properties. The extraction step performs no transformations --- its only job is to read the source faithfully and record row counts per hotel for later reconciliation.

\paragraph{Transform.}
The transform stage performs five operations in sequence, each with its own validation:

\begin{enumerate}
  \item \textbf{Date assembly.} The four arrival-date components (year, week number, day of week, day of month) are combined into a single arrival date per booking. Bookings whose assembled date falls outside the data window (July~2015 to August~2017) are flagged and counted.
  \item \textbf{Stay explosion.} Each booking is expanded into one row per night of stay, using the weekend-nights and week-nights variables: a booking with 2 weekend nights and 3 week nights becomes 5 rows, each carrying the booking's rate, segment, and status. This produces the booking-night grain of \texttt{fact\_room\_night}.
  \item \textbf{Surrogate key encoding.} Each dimension attribute (date, hotel, room type, market segment, customer type, deposit type, distribution channel) is encoded as a surrogate integer key against its dimension table. NULL values in the agent and company columns are treated as the category ``not applicable'' --- not as missing data, per the source paper's specification.
  \item \textbf{Realised-revenue split.} For each booking-night row, a realised-revenue measure is set to the room rate if the booking was not cancelled, and zero otherwise. This implements the first data correction of Section~3.2: revenue and occupancy are computed only from stays that actually occurred. The cancellation rate is asserted per hotel (expected approximately 27.8\% for H1 and 41.7\% for H2, per the source paper's tables).
  \item \textbf{Capacity estimation.} The number of rooms per hotel is not in the dataset; it is estimated as the maximum number of rooms sold on any single night, computed after a warm-up window that excludes the first weeks of data. The ETL recomputes this figure, asserts it against the realised-stay data, and stores it in \texttt{dim\_hotel} together with the estimation basis (currently estimated at approximately 187 rooms for H1 and 226 for H2).
\end{enumerate}

\paragraph{Cleaning log.}
Every cleaning rule records the number of rows it removes and the reason. The rules target anomalies documented in the source paper's summary statistics: negative ADR values (the minimum ADR is $-6.38$ for H1), extreme ADR outliers (the maximum is 5{,}400 for H2), impossible party sizes (the maximum number of adults is 55 for H1), and stays with zero total nights. The log is written alongside the warehouse so that any consumer can verify exactly how many rows were removed and why.

\paragraph{Load and quality gates.}
The transformed data is loaded into the DuckDB star schema. The pipeline then runs a suite of quality gates, each of which must pass before the warehouse is accepted:

\begin{itemize}
  \item \textbf{Referential integrity:} no orphan foreign keys.
  \item \textbf{Row-count reconciliation:} clean bookings equal distinct booking identifiers in the fact table.
  \item \textbf{Cancellation consistency:} \texttt{IsCanceled} = 1 if and only if \texttt{ReservationStatus} is ``Canceled'' or ``No-Show'' --- the identity verified in the data study ($11{,}122 = 10{,}831 + 291$ for H1; $33{,}102 = 32{,}186 + 916$ for H2).
  \item \textbf{Revenue reconciliation:} booked revenue minus cancelled revenue equals realised revenue.
  \item \textbf{Capacity assertion:} rooms sold never exceeds estimated capacity.
  \item \textbf{Density check:} the daily snapshot contains a row for every (hotel, date, room type), including zero-sale nights.
\end{itemize}

If any gate fails, the pipeline exits with a non-zero status and no partial warehouse is published.

\paragraph{OLAP demonstration.}
After the load succeeds, eight analytical queries demonstrate the warehouse's capability across the four classical OLAP operations: roll-up (month $\to$ quarter $\to$ year revenue and KPIs), drill-down (hotel $\to$ room type), slice (peak season), dice (segment $\times$ month), show-up rate (hotel $\times$ month), group-vs-transient share (hotel $\times$ season), day-of-week pattern, and booking-window lead time (group vs.\ non-group --- the empirical test of the Littlewood assumption). Each query produces a result table with a short commentary; full outputs are stored as CSV files alongside the warehouse for verification.
